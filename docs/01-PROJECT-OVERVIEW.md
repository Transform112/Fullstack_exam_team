## SECTION 1. LOCKED DECISIONS

These are final. Do not revisit.

1. Product name: Wishly. Sample domain used in docs: wishly.app.
2. Architecture: ONE Next.js application (App Router, TypeScript) that contains both the UI and the API. The API is implemented as Next.js Route Handlers under app/api/v1/. There is NO separate Express server.
3. Database: MongoDB Atlas (free tier) accessed through Mongoose.
4. Media: Cloudinary free tier. Browser uploads directly to Cloudinary using signed parameters generated by the server. Media never passes through the app server and is never written to local disk.
5. Styling: Tailwind CSS plus shadcn/ui for the app side (landing, wizard, dashboard, admin).
6. Animation: Framer Motion for component animation, Lenis for smooth scroll, canvas-confetti for confetti. GSAP is optional and must not be used unless a step in file 04 requires it.
7. Forms and validation: react-hook-form plus zod on the client; zod on the server for every request body.
8. Auth: email plus password, bcrypt hashed, JWT stored in an httpOnly cookie named wishly_token. The Authorization header is NOT used. This one choice is used everywhere, consistently.
9. Other libraries: nanoid, slugify, qrcode (server, for the qrCode data URL), qrcode.react (client display), react-dropzone, browser-image-compression, dnd-kit (reorder), sanitize-html (plain-text cleaning), leo-profanity, jsonwebtoken, bcryptjs, pino. Vitest covers server logic and Playwright covers browser workflows. Rate limiting uses MongoDB as described in file 02; there is no Express or Redis.
10. OG image: Next.js ImageResponse at app/api/og/[slug]/route.tsx.
11. Languages for generated pages: HINGLISH, ENGLISH, HINDI. Copy lives in locales/en.json, locales/hinglish.json, locales/hi.json, looked up by key. Hindi uses the Noto Sans Devanagari font.
12. Templates (exactly 3): neon-night, pastel-dream, royal-gold. Template ids are these exact slugs.
13. Public wish page route: /w/[slug]. This is the required baseline. Auto-deploy to Vercel or Netlify is a bonus and is done last (file 05).
14. Seeded accounts (created by the seed script):
    - admin@demo.com / Admin@123 (role ADMIN)
    - creator@demo.com / Creator@123 (role USER)
15. Deployment targets: the single Next.js app on Vercel, database on MongoDB Atlas, media on Cloudinary.
16. API conventions:
    - Base path: /api/v1
    - Success body: { "success": true, "data": ..., "message": "optional" }
    - Error body: { "success": false, "error": { "code": "VALIDATION_ERROR", "message": "...", "details": [...] } }
    - Status codes: 200, 201, 400, 401, 403, 404, 409, 429, 500
    - List endpoints accept page, limit, sort, search and return { items, page, limit, total, totalPages }

## SECTION 2. WHAT THE PRODUCT DOES

A logged-in Creator fills a 6-step wizard (occasion, recipient, words and language, media, style, review). On Generate, the system creates a unique link /w/[slug]. Anyone with the link sees a cinematic, animated, personalised greeting website for the recipient. The Creator gets a share kit: copy link, downloadable QR PNG, WhatsApp share, Instagram share.

The generated page must produce a "wow" effect in the first 3 seconds. The UI quality of the generated page is the single largest scoring item (25 of 100 marks). A plain heading plus image grid will score low.

There are two design worlds:
- The app (landing, auth, wizard, dashboard, admin): clean, modern, playful.
- The generated wish pages: cinematic and emotional. Each template is its own mini design system.

## SECTION 3. ROLES AND PERMISSIONS

Roles:
- Creator: a logged-in user (role USER) who makes pages.
- Viewer: any public visitor with the link. Not logged in.
- Admin: platform operator (role ADMIN). Seeded, never self-registered.

Permission rules (enforced on the SERVER on every endpoint, not only by hiding buttons):

- Create page: Creator.
- Edit own page: Creator (owner only).
- Delete page: owner, or Admin.
- Disable any page: Admin only.
- View published page: everyone.
- View draft or unpublished page: owner, or Admin.
- Post a wish on the wishes wall: Viewer and Creator. Not Admin.
- Delete a wish: owner of the page, or Admin.
- See analytics: owner sees own pages; Admin sees all.
- Manage templates: Admin only.
- Trigger deploy (bonus): owner, or Admin.

## SECTION 4. GLOSSARY

- Occasion: BIRTHDAY, ANNIVERSARY, WEDDING, FAREWELL, CONGRATS, FRIENDSHIP, CUSTOM (user-typed label).
- Wish page: the generated public website for one recipient, at /w/[slug].
- Slug: unique URL-safe id. Format: slugify(recipientName + "-" + occasion) + "-" + nanoid(4). Example: riya-birthday-7f3a. Permanent once published.
- Template: a visual style (layout, colours, fonts, animation set). Exactly 3 are built.
- Section: a building block of a wish page: Lock screen, Intro, Hero, Message, Memory timeline, Gallery, Video, Wishes wall, Finale.
- Parallax: layers moving at different speeds on scroll to create depth.
- Reveal date (revealAt): optional date and time. Before it, the page shows only a countdown.
- OG tags: Open Graph meta tags that produce a rich link preview on WhatsApp and Instagram.
- Page status values: DRAFT, SCHEDULED, PUBLISHED, UNPUBLISHED, DISABLED.

## SECTION 7. USER FLOWS

### 7.1 Creator flow (in order)
1. Sign up or log in
2. Choose occasion and date
3. Recipient details
4. Words and language
5. Upload photos and videos
6. Pick template and colours
7. Preview and generate
8. Share link, QR, or deploy

### 7.2 Viewer flow (in order)
1. Opens shared link
2. Countdown (only if locked)
3. Password gate (only if password set)
4. Animated intro with "Tap to begin"
5. Scroll the story
6. Leave a wish
7. Finale surprise
8. Share or replay

### 7.3 Generation pipeline (what the server does on publish)
1. Validate the full payload with zod: required fields, media count and size limits, valid template id.
2. Create slug: slugify(name + "-" + occasion) + "-" + nanoid(4). If the slug already exists, regenerate the suffix until unique.
3. Save the page with status PUBLISHED, or SCHEDULED if revealAt is in the future.
4. Make the OG image URL available at /api/og/[slug].
5. Return { slug, url, status, revealAt, qrCode, ogImage } where qrCode is a PNG data URL.
6. (Bonus) enqueue a deploy job.

## SECTION 9. GENERATED PAGE, SECTION BY SECTION

Sections appear in this order on /w/[slug]:

1. Lock screen: if revealAt is in the future, show an animated countdown (days, hours, minutes, seconds) and teaser text "Something special is coming for [Name]...". If a password is set, show a password gate.
2. Intro and loader: 1.5 to 3 seconds. Recipient name letters animate in. Button "Tap to begin". The tap is required to unlock audio autoplay.
3. Hero: full-screen parallax. Background layer (gradient, stars, or bokeh), middle layer (balloons, petals, or shapes), front layer (giant animated greeting). Tilt on mouse (desktop) and gyro (mobile).
4. Message: the special words revealed with a typewriter or word-by-word fade. Signature line "- [from]".
5. Memory timeline: vertical timeline; each memory card slides in on scroll with photo and date.
6. Gallery: masonry, polaroid stack, or 3D carousel depending on template. Staggered reveal, lightbox on tap, scroll-linked scale or parallax on images.
7. Video: autoplays muted when in view, tap to unmute, rounded frame with glow.
8. Wishes wall: friends' wishes as floating cards or sticky notes, plus a form to add a wish.
9. Finale: cake with candles to blow out, confetti cannon, fireworks, closing line, replay and share buttons.
Global: background music toggle, scroll progress indicator, smooth scroll, reduced-motion fallback, footer "Made with love on Wishly".

Detailed animation instructions for each section are in file 04.

## SECTION 10. BUSINESS RULES AND EDGE CASES

Rules:
1. Required to publish: occasion, recipient name, at least 1 message, at least 1 image, template. Everything else optional.
2. Limits: recipient name 40 characters; each message 600 characters; 1 to 5 messages; up to 8 memories; wish message 280 characters.
3. All user strings rendered on public pages must be sanitised (strip HTML with sanitize-html). Render them as React text; never use dangerouslySetInnerHTML.
4. Media limits are enforced on BOTH client and server. Unsupported MIME types are rejected.
5. Slug is permanent once published. Editing content keeps the same link.
6. Scheduled pages: the public API must not return any content before revealAt. Return only locked:true, recipient first name, revealAt. Never rely on a frontend timer alone.
7. Password-protected pages: store a bcrypt hash; return content only after the unlock token is verified.
8. Wishes: maximum 3 per visitor per page per hour; length limits; basic profanity filter.
9. Deleting a page also deletes its Cloudinary assets.
10. Views: count once per visitor per 30 minutes using a visitor id cookie; never count the owner's own preview.
11. Never return passwordHash or owner email in any public API response.

Edge cases and required behaviour:
- Slug collision: regenerate the suffix until unique.
- Recipient name in Hindi script while language is English: allowed; Devanagari must render correctly.
- Only 1 photo uploaded: gallery shows a single hero-style photo, no empty grid slots.
- Portrait and landscape mix: layout handles aspect ratios with object-fit or masonry.
- Slow 3G visitor: loader shown, progressive images using Cloudinary f_auto,q_auto,w_[size]; video lazy-loaded.
- Browser blocks autoplay audio: music starts only after "Tap to begin".
- Page disabled by admin: friendly unavailable screen.
- Unknown slug: designed 404 with call to action.
